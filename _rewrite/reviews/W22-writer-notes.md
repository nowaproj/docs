## (a) ID type in the detail-screen recipes

Edited: `docs/logic/navigation.md` (new paragraph between the "Before you start" paragraph and step 1 of `{#open-a-detail-screen}`; the numbered steps are untouched) and `docs/guides/complete-app.md` (one sentence added to step 1 of "6. Open the detail screen").

Text added:
- navigation.md: "Before you drag the route's chip onto the screen's param, set the param's **Type** in **Details**. The type must match the `id` your **Get Record by ID** function takes, which follows your table's `id` column: `int` for a whole number, `String` for text or a uuid. If the types differ, **Problems** shows an error."
- complete-app.md: "Its **Type** must match the `id` that `getByIdRecipes` takes: keep `String`, the default, because the table's `id` is a uuid."

Code answers, in the order the brief asked:

1. **Type of the `id` the Get Record by ID template generates.** The generated function is `Future<Model?> getById<Table>(<idType> id)`, `id` non-null (`packages/data/lib/src/supabase/templates/template_source_generator.dart:54-65`). `idType` is `int` when the table's `id` property maps to `int`, else `String` (`:40-43`; it takes the column named `id`, or the first column when there is none). The mapping is `integer` to `int`, `string` to `String`, `boolean` to `bool`, anything else `dynamic` (so `String` for the id) (`packages/data/lib/src/supabase/models/sb_table.dart:55-70`). Tables come from the project's PostgREST OpenAPI document, `$url/rest/v1/` `definitions` (`packages/data/lib/src/supabase/supabase_service.dart:49-67`). The template: `packages/data/lib/src/supabase/templates/supabase_template_definitions.dart:29-37` (**Get Record by ID**). `docs/integrations/supabase/database.md` already says "its type decides whether `id` is a number or text".
2. **Default type and nullability of a new screen or component param.** The **+** on **Params** in the **Variables** panel creates `VariableDeclImpl($String.thisType.copyWith(isNullable: true), 'param…', initializer: StringBlock(''))`: a `String` that can be empty, default `''` (`packages/core/lib/src/widgets/code/declaration_list_widgets.dart:277-307`, used for screens and components at `packages/designer/lib/src/panels/variables_panel.dart:72`).
3. **Can the user pick type and nullability?** Type: yes. A selected param shows **Name**, **Type** and **Default Value** in **Details** (`packages/core/lib/src/panels/details/decl_details.dart:45-47` to `VariableField`, `packages/core/lib/src/widgets/code/variable_widgets.dart:309-337, 416-465`; label `"Type"` at `:452`). **Type** opens **Select type** with the basic types `String`, `int`, `double`, `bool`, `Color`, `Widget`, **show more...** and an **As List** checkbox (`packages/core/lib/src/fields/nowa_fields.dart:631-771`; `_basicTypes` at `:682`, title `:717`, checkbox `:735`). Nullability: **no control**. Every type the picker returns is nullable (`typeFromClass` returns `ClassTypeImpl(klass: klass, isNullable: true)` or a nullable list, `nowa_fields.dart:696-706`), and `TypeView` shows only the type name, never a `?` (`packages/core/lib/src/widgets/code/type_widgets.dart:9-14`). I found no other nullability toggle in the editor UI (grep of `isNullable` under `core/lib/src/widgets`, `core/lib/src/fields`, `designer/lib/src/details`, `designer/lib/src/panels`, `code/lib/src`). So a reader never sees `String?` and never has to choose it. (The link menu's **Create Param...** makes a param with the field's own type, which can be non-null: `packages/core/lib/src/fields/field_link_menu.dart:188-208`. Not used by the recipes.)
4. **Nullable value linked to a non-null parameter: no problem, no conversion, Nowa writes a `!`.**
   - No Problems row: for two class types with the same name and no type arguments, `isAssignableTo` returns true whatever the `?` says (`packages/core/lib/src/interpreter/type.dart:160-182, 227-247`). The argument check is `param.type.isAssignableTo(arg)` (`packages/core/lib/src/interpreter/block_tree.dart:5795-5812`).
   - The generated source gets the `!` from the slot the reference fills: `ReferenceBlock.source` appends `getNullabilitySuffix(expectsNull: getExpectsNull)` (`block_tree.dart:3640-3671`); the suffix is `!` for a nullable type in a slot that does not expect null (`:3322-3330`, `:3338-3349`); a call argument's slot gets its expectation from the function's parameter type (`packages/core/lib/src/interpreter/block_host.dart:47-61`, `:150-153`). The designer never types an operator, so the form is derived from the slot (doc comment `block_tree.dart:3308-3316`). So a nullable `id` param linked to `String id` or `int id` is written `getByIdRecipes(id!)`. Related repo test of the same mechanism: `packages/core/test/interpreter_tests/type_test.dart:99-106`.
5. **A different type (String param, int function) does show up, and nothing converts it.** `ArgumentTypeNotAssignable`: "The argument type 'String?' can't be assigned to the parameter type 'int'." (`packages/core/lib/src/interpreter/block_problems.dart:196-202`). It appears in **Problems** under **From Nowa (Instant)** (`packages/core/lib/src/panels/problems_panel.dart:45-47`, `packages/core/lib/src/file_system/dart_file.dart:309-329`) and in red under the Data Builder's input (`packages/core/lib/src/fields/class_field.dart:107-117, 141-161`; the Supabase source uses that builder, `packages/data/lib/src/supabase/ui/sb_field.dart:53`). The link menu does not convert: on a type mismatch it applies the link and opens the value's members one level deeper (`packages/core/lib/src/fields/link_menu.dart:152-159`, `field_link_menu.dart:160-186`). The page says only "**Problems** shows an error" (shortest exact claim).
6. **Why "before you drag the chip".** For the integer case the Router panel converts the path's text when the chip is dropped: it builds `id != null ? int.tryParse(id) : null` from the screen param's type (`packages/core/lib/src/editors/router_editor/go_route_node_view.dart:344-355`, `auto_type_parser.dart:33-45, 60-102`; the page already says "Nowa adds the conversion for you" in "Pass data to the next screen"). Changing a param's type later does not touch existing uses (`packages/core/lib/src/interpreter/generators/variable_generator.dart:16-41`), so the type has to be set first (or the chip dragged again).

Left out on purpose: the automatic `!` (invisible in the editor, so nothing for the reader to do); the `Create Param...` route; the edge case of a table without an `id` column.

Open issues / observations (none blocks the recipes; nothing here is unfixable in the visual editor):
- **Not run in the app.** Everything above is from code. The one external fact is that PostgREST reports `smallint`/`integer`/`bigint` columns as JSON type `integer` and `uuid`/`text` as `string`; the repo only shows Nowa's side (`sb_table.dart:60-70`). `database.md` already relies on it.
- **Runtime consequence of the `!`.** A missing id would throw ("Null check operator used on a null value") when the screen builds. With a path param the id is always there. A recipe that used an optional query param would need a default or a check. The recipes use the path param, so nothing to document.
- **complete-app.md, outside this item:** step 2 gives `RecipeCard` the params `id`, `title`, `description` (all default `String`), and step 5.5 links `element.id` to `RecipeCard`'s `id`. That works for the guide's uuid table. With an integer `id`, `element.id` is `int?` and `RecipeCard`'s `id` would need **Type** `int` too (link menu goes one level deeper, **Problems** shows the mismatch). I did not add an `int` branch to the guide (the table is defined by the guide), and did not change steps 2 or 5.

## (c) REST API warning

Edited: `docs/integrations/rest-api/index.md`, the existing `:::warning` (still one admonition). It now reads: "The **Base URL** and the headers you add, on the collection or on a single request, are written into the collection's Dart file and ship inside your app, even a token you paste into a header value. Never put a server secret there. The **Auth Key** is only a name: Nowa writes no token into your code, and your app reads the token from Shared Preferences on the device."

What the code shows:
- **Base URL** is set on the collection's `BaseOptions` in `_dioClient` (`packages/data/lib/src/api/model/api_collection.dart:14-20` getters, `:41-53` creates `_dioClient`, `:55-58` `setBaseUrl`; saved by `packages/data/lib/src/api/views/widgets/api_edit_collection_dialog.dart:79-91`). **Collection headers** go to `BaseOptions.headers` (`api_collection.dart:24-30` getter, `:60-63` `setHeaders`). **Request headers** go to the request's `Options(headers: …)` (`packages/data/lib/src/api/model/request_func.dart:141-157`; the request is a member of the collection class, `api_collection.dart:65-67`). All of it lives in the collection's `*.api.dart` file, which is part of the app's code (the page already names `lib/api/cats.api.dart`). Header cells are string fields with the hints `Key` and `Value` (`packages/data/lib/src/api/views/widgets/headers_field.dart:157-163, 183`; **Add header** at `:37`), so a token pasted into a value is written like any other value.
- **Auth Key** is only the name of a Shared Preferences entry: the dialog's helper text says "The key used to store the auth token in SharedPreferences" (`api_edit_collection_dialog.dart:162-176`) and saving it generates an interceptor that sets `options.headers['Authorization'] = 'Bearer ${sharedPrefs.getString('<key>')}'` (`packages/data/lib/src/api/interceptors/generate_auth_interceptor.dart:4-25`, `api_collection.dart:100-115`; the dialog calls it when **Auth Key** is not empty, `api_edit_collection_dialog.dart:87-91`). The token is read at run time from `sharedPrefs = await SharedPreferences.getInstance()` (`packages/core/lib/src/file_system/templates/common/main_dart_template.dart:25-30`, `packages/core/lib/src/project/env_services/main_func_block.dart:20`), i.e. the device's Shared Preferences. Nowa never writes a token value into the file.
- **Test token** (**Auth token value**) is not in the project at all: `submitAuthToken` stores it in the editor's own local preferences under `<authKey>_NOWAGENERATED` inside `user_shared_prefs_<projectId>` (`packages/data/lib/src/api/model/test_api_func_provider.dart:137-144`, `packages/data/lib/src/api/views/api_panel/api_test_section/api_test_values_panel.dart:137-142, 171-195`, `packages/core/lib/src/interpreter/libraries/shared_preferences_library.dart:145-151, 207-209`, `packages/core/lib/src/services/shared_preferences_services.dart:6-8`). The page's "Test a request" step 2 ("Nowa keeps that token for testing only, not in your app") is therefore right and was not edited. The warning does not repeat it.

Left out: "anyone who has the app can read them". That is true of any compiled app but is not something Nowa's code shows; the sibling pages (`guides/data-and-state-tips.md#keep-secrets-out-of-your-app`, `integrations/constants.md`) carry that advice, and `data-and-state-tips.md` already words this bullet as "The base URL and the header values you type in a REST collection are saved in your project's code and go into the app", which matches.
